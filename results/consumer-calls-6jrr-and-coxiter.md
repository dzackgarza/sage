Both are steps of the consumer-acceptance job that had no result of their own yet. What follows is
what each call did in the published image, on explicit revisions, with the limits of what the
observation establishes stated alongside it.

    outcome:    peakrss STOPPED_AT_MEMORY_LIMIT, tree RSS 6171 MiB over a 6144 MiB bound, 306 s
    files:      no card diff, no certificate written

**What that establishes:** that guarded attempt stopped, and nothing more. It is **not** an
intrinsic memory requirement of the 6JRR computation, **not** a kernel OOM, and **not** a
certificate: a 20-minute deadline in a 6.1 GiB box is not the owner's production setting.

**What the owner's own system does here, and why this run bypassed it.** `genus.py:352` describes
the policy — a fraction of the machine's memory that workers leave available, below which the
worker holding the most memory is killed — and `genus.py:494` records the reason in the ledger
(`"memory exhausted"`); `AGENTS.md:162` says worker errors and memory failures enter `failures/`
with their input and stderr. My guard killed the process from outside, so nothing entered
`failures/`: the card is neither certified nor recorded as failed.

**Difference from the production path worth the owner's attention.** `certify.yml` runs
`--workers 1 --shard i/N --phase fields`, with a 340-minute job budget and a persister every 30
minutes, on a GitHub runner. The consumer-acceptance step runs no shard and no `--workers`, so it
takes `os.cpu_count()` (4 here) with a 20-minute deadline. That is a different memory and time
shape from production, and it is the shape that reached 6.1 GiB.

## CoxIter: exit 0, and reading the wrong object

### What the tool reads, from its own source

CoxIter's `parseGraph` (`coxiter.cpp`, pinned build `b800be48d8`) takes the digits on the first
line as the vertex count, an optional `vertices labels:` line, then one `<a> <b> <order>` per
edge; every other line is echoed as `Unread line (incorrect format)`.

### The step as it was

    coxiter: /usr/local/bin/coxiter
    coxiter exited 0
        Number of vertices: 8
        Dimension: ?
        Field generated by the entries of the Gram matrix: Q
        f-vector: (1, 8, 28, 56, 70, 56, 28, 8, 1)
        Euler characteristic: 1/256

A complete graph on eight vertices — the 7-simplex — is not the record's chamber, which states
nine walls. This record is not a CoxIter graph either: its Gram rows are plain indented numbers,
its prose lines are not edges, and none of them matches the edge grammar.

### Runs under unusual provenance, and what the local image actually is

The CoxIter measurements, and the certification run below, are a **local unpacked rootfs with
checkouts bound over `/repos/*`**, not a published-image run:

| what | value | evidence, and its limit |
| --- | --- | --- |
| rootfs | `~/sage-image/rootfs` | the tree that ran; `docker/sage-image.py --rootfs` points at it directly |
| image identity | OCI config `sha256:2d6a4754b6f1518af356dd28ac6ec2e7678c7fe4ab0d70c2e7c9ecbc2c605eca`, 18 layers | `~/sage-image/config.json`, read now |
| index digest | `sha256:220293469c53…`, source `6a1d6d9f` | **cited** from results/runtime-adoption-220293469c53-acceptance.md; not re-verified in this turn — the cache carries no stamp (`sage-image.py info --cache ~/sage-image` reports none), so it is a recorded value, not something read off the tree |
| image's own /repos, none bound | sage-extensions `7b222e86`, lattice-database `230d41ae`, research `ec1333ee` (no `computations/`) | read from the image with nothing bound |

The bindings each run used are stated where the run is: for the CoxIter check, research
`dbf178cf30`; for the certification and owner-contract calls, provider `240cd3f8`, lattice-database
`d1711db05f`, research `dbf178cf30`, port `991b88b0`. An image that already carried these
revisions would behave the same way; the bind is a statement about this rootfs, not a requirement
on the published image.

### The parser path, reproduced rather than inferred

Changing **only** the number in the record's opening line, `initial roots: 8` to
`initial roots: 11`, and running the same binary on the same file otherwise byte-identical:

    initial roots: 8   ->  Number of vertices: 8    f-vector (1, 8, 28, …)      Euler 1/256
    initial roots: 11  ->  Number of vertices: 11   f-vector (1, 11, 55, …)     Euler 1/2048

So the leading line's digits are the vertex count, and the graph CoxIter builds is not the
chamber. That is as far as the evidence goes: the earlier draft of this file said the Gram rows
were `#`-commented, which they are not — the `#` came from CoxIter's own `Unread line` echo — and
no claim is made about how the rest of the file would be parsed if the count were valid.

### Which side owns it

No library exporter exists — `dxack_research` produces records, not CoxIter graphs — so nothing
exported this wrongly, and nothing mathematical is at issue. The wrong input is passed by the
image-owned step, and that is what is repaired here.

### The repaired step, and what it now asserts

The step derives the graph from the two lines of the record that do state it — `walls: 9` and
`edges (i, j, label)` — checks that list against the record's own `label counts`, hands CoxIter
that file, and requires the reading to be the chamber rather than accepting exit 0:

    --- the graph handed to CoxIter
    9 / 1 2 3 / 2 3 3 / 3 4 3 / 3 9 3 / 4 5 3 / 5 6 3 / 6 7 3 / 7 8 4
        Number of vertices: 9
        Field generated by the entries of the Gram matrix: Q[sqrt(2)]
        Guessed dimension: 8
        Number of vertices at infinity: 1
        Euler characteristic: 17/1393459200

A vertex count, or the field of the Gram entries, does not establish which graph was read: two
different graphs can share both. The acceptance is therefore CoxIter's `-pcm` output — the Coxeter
matrix of the graph it parsed, `m_ij` being 2 where there is no edge — held entry by entry to the
matrix the record's `edges (i, j, label)` list defines. On the repaired input the engine prints

    1,3,2,2,2,2,2,2,2   3,1,3,2,2,2,2,2,2   2,3,1,3,2,2,2,2,3   ...   2,2,2,2,2,3,1,4,2   ...

which is exactly the record's list: order-3 edges along the chain, `3–9` closing it, and the
order-4 edge `7–8` appearing as the 4 in row 7.

`docker/tests/test_coxiter_chamber_input.py` keeps this honest: it runs the step's own block in
the image, takes the input the step says it handed over, asks the engine for its matrix, and
holds that to the record. Against the repaired step it passes in 0.97 s; against the pre-fix step,
whose input is the record itself, the same assertion fails with "the parsed labelled adjacencies
are not the record's edge list". CoxIter's own verdict — cocompactness, covolume, the
characteristic — stays evidence, not a gate, and the record's numerical claims keep their own
evidence class: this step says which chamber was read, never that the research record certifies
it.
